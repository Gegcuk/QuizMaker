## Proposed release gate

Create one release-readiness parent issue, temporary ID **REL-01**, with explicit child dependencies and the owner-approved first-release capability list. Keep [#466](https://github.com/Gegcuk/QuizMaker/issues/466) as the historical audit tracker and [#472](https://github.com/Gegcuk/QuizMaker/issues/472) as the execution programme. Neither should be treated as the entire product's release checklist.

REL-01 is done only when:

1. Every in-scope defect and required operational gate below has implementation evidence, an exact passing regression, and a reviewer. A deferral identifies an owner, rationale and review trigger.
2. No unresolved Critical or High finding is reachable through the released UI, API, background job or administrative path. A disabled feature requires server-side denial and contract tests; hiding a button is insufficient. Disabling a feature is an owner decision, not an automatic substitute for fixing it.
3. Scores, historical results, refund/payment effects, ownership, identity and retry behavior agree with the approved contracts under real database concurrency.
4. Release-mode Java/MySQL/container/migration checks, bounded-query and load checks, crash recovery, backup/restore, deployment rollback/forward repair and the applicable operational controls are evidenced. Previously accepted monitoring/parser-isolation deferrals remain recorded under their approved assumptions; changing them requires a distinct evidence-based proposal, not a claim that the owner never decided.
5. The actual web client passes the selected end-to-end journeys against the candidate backend: account onboarding, authoring/import, generation, practice, review, and payments/guests/other features when included.
6. The repository owner gives a separate go/no-go decision. Questionnaire answers authorize recording policy in issues; they do not authorize destructive reset, code implementation, payment actions, deployment or release.

“Every finding covered by an issue” is the completion criterion for stage 3. “Ready for real users” requires completing and validating those issues afterwards. No source review can promise that all future defects have been discovered.
