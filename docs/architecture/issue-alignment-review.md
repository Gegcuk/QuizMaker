# Согласование архитектуры и issues после аудита

Актуальный срез: **23 октября 2026**. Этот документ описывает исправленные требования и оставшиеся условия реализации; он не доказывает работоспособность ещё не реализованного приложения. Источники: [реестр решений](decision-register.md), [архитектура](policy-driven-quiz-execution.md), [оставшиеся вопросы](open-questions.md) и свежие тексты GitHub.

## Принятые уточнения Learning

- На первом этапе **нет дневной учебной квоты**. Ограничивается размер страницы/сессии; после 20 вопросов из 100 due ученик может продолжить в тот же день. Число 20 — пример, не новый default. Ограничение частоты команд остаётся отдельным механизмом.
- Публичный показатель освоения отложен. [#847](https://github.com/Gegcuk/QuizMaker/issues/847) определяет будущий смысл, единицы, достаточность данных и агрегацию до реализации метрики. Желаемое запоминание 90%, экзаменационный балл и завершённый план интервалов не подменяют освоение.
- Первый FSRS/custom-сценарий не ждёт определения этой метрики. Clean start сохранён: существующих quiz/question repetitions нет, обязательный SM-2 import и старые адаптеры не требуются. Обычные API квизов и тренировок защищаются отдельно.

В #850 сохраняется атомарное первое построение для `NORMALIZED`. Текущий API не предоставляет reset/rebuild для `STRUCTURED`; отказ до AI нельзя выдавать за доказательство rollback. Mock saveAll и self-invoked REQUIRES_NEW не доказывают сохранение слоёв после rollback.

Замена сертификата использует настоящий #557. Fixture удалённого профиля проверяет только этот consumer. Атомарность certificate/event остаётся #837, доставка — #800. |
| #558 как читающий endpoint требовала исполнять чужие команды | Собственные projection/privacy/cache проверки отделены от условных интеграций. CERT-VERIFY-LIFECYCLE вызывает реальные #557/#635 и публичный endpoint, проверяет revoke/supersede, прогретый cache, достигнутый write-failure, свежие чтения, успешный retry и restart. Подготовленный revoked fixture не заменяет этот сценарий. |
| В сценарии удаления аккаунта не было настоящего исполнителя | В открытых и закрытых задачах не найден отдельный владелец account/profile command; #699 владеет только core-history family, а UserService создаёт пользователей и не исполняет удаление. Создан #851 для реального удаления аккаунта/профиля и возобновляемой композиции #844/#699. Шесть собственных сценариев требуют фактические записи, ограничения доступа, scope/partial-progress, rollback, restart и restore guard. Существующий флаг User.isDeleted не объявляется готовой реализацией. |
| Связь могла сохраниться только в искусственном состоянии | #558 владеет CERT-VERIFY-ACCOUNT через реальный #851/#699 и CERT-VERIFY-DELETION-RACE дополнительно через #635. Проверяются прежняя ссылка, контакты/личная история, сохранность formal evidence, отсутствие реактивации и текущий статус после успешных команд и retry. Уведомления и физическое стирание backup не объявляются доказанными этими HTTP-тестами. |

У #635/#558 прежние обязательные prerequisites сохранены. Единственная новая native-связь: #851 требует #844, транзитивно получая #699/#664/#698/#608. Публичное чтение, lifecycle и account command не зависят друг от друга взаимно; условные совместные проверки обязательны перед включением соответствующей возможности. #837/#800 сохраняют собственные integration gates. Эти уточнения не добавляют blockers #598, подготовке #577, инвентаризации #843, D38 или первому release producer.

Для #851 перед реализацией остаётся сопоставить конкретные таблицы, auth-пути, семейства и command/status contract. Если нужен новый доступ к статусу после удаления логина, его нельзя молча вывести из права удаления: такой интерфейс требует отдельного точного решения. Это не новое правило доступа и не повод сохранять прежние credentials. Неподдержанная или неподтверждённая часть удаления остаётся pending; whole-account completion нельзя получить из core-only fixture.

Пример: Иван удаляет аккаунт после экзамена. Реальный executor удаляет допустимые личные данные, а ранее выданная пригодная ссылка продолжает показывать минимальный статус сертификата. Последующий настоящий отзыв меняет ответ той же ссылки; сбой до commit сохраняет прежний статус, retry завершает переход один раз. Контакты, имя из задания, приватный результат и причина исправления в публичный ответ не попадают.
