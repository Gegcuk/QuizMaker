# Опросник решений владельца по архитектуре выполнения квизов на основе политик

**Статус:** Открытые решения владельца после исправления бэклога от 08.08.2026.

Это канонический список решений по продукту, конфиденциальности, безопасности, эксплуатации и пользовательскому опыту, на которые всё ещё должен ответить владелец. В него входят и долгосрочные решения по расширению системы, а не только блокеры первого релиза. В implementation issues нельзя выводить ответ из рекомендации и принимать его без явного решения владельца.

## Как отвечать

Укажите ID вопроса и вариант ответа, например `A01: A`, `D03: B`, либо дайте собственный ответ. Можно отвечать по одной группе за раз. Ответ считается полным только тогда, когда явно заданы все числовые ограничения, значения по умолчанию, исключения и legacy-поведение. После этого выбранный ответ будет скопирован в соответствующий GitHub issue и в журнал архитектурных решений.

Приоритет:

- **Фаза 0:** ответить на строки `Core` до первого implementation PR по новой policy-driven архитектуре, за исключением независимого усиления безопасности #690.
- **До реализации функции:** ответить на строку до начала соответствующего implementation issue.
- **До активации:** реализация может быть создана в отключённом режиме (`dark`), но ответ должен быть принят до того, как на неё начнут направлять пользователей.
- **Будущее:** текущая разработка не блокируется, но архитектура не должна молча выбирать значение самостоятельно.

> **Аннотированная версия.** Исходные вопросы, варианты, рекомендации, ID и поля для ответа сохранены без изменения смысла. Ниже добавлены пояснения простыми словами, архитектурный контекст, развёрнутые сценарии и практические последствия рекомендаций.
>
> Пояснения помогают принять решение, но не являются уже принятыми ответами. Если пояснение расходится с утверждённым architecture document или с более конкретным решением owning issue, приоритет имеет утверждённый источник.

## Как пользоваться этой версией

В большинстве пунктов вы выбираете не «идеальную модель навсегда», а **безопасный и достаточно полезный контракт первой версии**. Архитектура специально допускает вводить только необходимый subset, а дальнейшие возможности добавлять новыми типизированными полями, presets и versioned strategies.

Практический порядок:

1. Сначала ответить на вопросы **Фазы 0**, чтобы первый policy-driven walking skeleton не делал скрытых предположений.
2. В ответе указать не только букву, но и конкретные numbers/defaults/exceptions, когда они требуются.
3. Если функция пока не нужна, лучше явно выбрать узкий v1 или отложить решение с owner и trigger, чем заранее реализовывать широкий generic mechanism.
4. Для formal assessment, authorization, disclosure, timing и integrity безопасный default — **fail closed**: при неизвестной версии или неоднозначном контексте операция запрещается, а не угадывает значение.
5. Legacy compatibility сохраняет существующие успешные сценарии, но не требует переносить в новую модель ошибки безопасности или выдумывать отсутствующую историю.

## Короткий словарь архитектуры

- **Policy / политика попытки** — полный набор правил, по которым выполняется одна попытка: selection, order, delivery, navigation, timing, grading, disclosure, limits и так далее.
- **Preset / пресет** — повторно используемый шаблон policy. `PRACTICE` или `FORMAL_ASSESSMENT` — удобные продуктовые названия preset, а не отдельные движки.
- **ResolvedAttemptPolicy** — итоговая policy после объединения platform defaults, preset, immutable revision constraints, assignment, audience, accommodation и разрешённых overrides.
- **Snapshot** — неизменяемо сохранённая итоговая policy конкретной попытки. После старта она не перечитывается из mutable settings.
- **QuizRevision / QuestionRevision** — опубликованная неизменяемая версия квиза/вопроса. Новое редактирование создаёт следующую revision, не меняя старые attempts.
- **AttemptForm / форма попытки** — точный набор выбранных вопросов, их порядок, section/case membership и порядок options, фактически предназначенные участнику.
- **ParticipantSubject / субъект участника** — server-resolved identity одной попытки: authenticated user или capability-bound guest. Это не client-supplied `userId`.
- **Capability** — ограниченный секрет/право на конкретные операции. Capability не равна личности и не даёт автоматически author/review permissions.
- **Idempotency** — одинаковая повторная команда имеет тот же результат и не создаёт второй side effect; тот же key с другим payload возвращает conflict.
- **Receipt / квитанция команды** — сохранённая bounded запись, позволяющая распознать idempotent retry и вернуть прежний outcome.
- **Fail closed** — при неизвестной версии, неоднозначной identity или недостаточном evidence система отказывает, а не выбирает permissive default.
- **Supersession** — новая immutable запись становится текущей интерпретацией, но старая не удаляется. Используется для grade/result corrections.
- **Projection** — производная read model для reports/leaderboards. Она строится из immutable facts и может обновляться асинхронно.
- **Outbox** — durable событие, записанное вместе с domain transaction и позже опубликованное transport/projector без потери commit.
- **Dark rollout** — новый код уже развёрнут, но реальные пользователи ещё не направляются в него.
- **Rollback в этой архитектуре** — остановить новые starts на target path и выполнить forward-fix для уже созданных target attempts, а не превращать их обратно в legacy rows.
- **Basis points** — целое normalized значение: `10000 = 100.00%`, `7000 = 70.00%`.
- **Scope** — точная граница права: конкретная organization, assignment, attempt и operation; одной global permission недостаточно.
- **Reconciliation** — периодическая проверка persisted state, которая находит stuck/missed/inconsistent records и безопасно запускает idempotent recovery.
- **Fixture / conformance fixture** — конкретный end-to-end сценарий с точными policy values и ожидаемыми результатами, которым сертифицируется готовность capability.

## Уже принятые решения

Это не вопросы, и их не следует случайно открывать заново:

- Существующее поведение API и фронтенда продолжает поддерживаться, пока активация новой реализации выключена. Для сохранения работы текущих квизов изменения фронтенда не требуются.
- Существующие попытки остаются явно обозначенными legacy-свидетельствами; миграция никогда не выдумывает историю ревизий, политик, форм, субъектов, ответов или результатов.
- Опубликованный контент, разрешённая политика, формы участников, принятые ответы и факты результата являются неизменяемыми и версионируемыми.
- Одинаковые канонические повторные запросы возвращают тот же успешный результат; повторное использование того же ключа с другими входными данными возвращает конфликт.
- Принятые ответы не редактируются на месте. Любая будущая коррекция выполняется через явное неизменяемое замещение (`supersession`) и аудит.
- Атомарные пакеты ответов работают по принципу «всё или ничего». Частичное принятие отдельных элементов сейчас не входит в контракт пакетной отправки.
- Порог прохождения по умолчанию — 70% для каждой неизменяемой ревизии.
- При равенстве лучших результатов сначала выигрывает более быстрое прохождение, затем более раннее завершение.
- Legacy-результаты, которые невозможно достоверно восстановить, остаются доступными для просмотра как legacy, но исключаются из сопоставимого рейтинга.
- Существующие вопросы Fill Gap без дистракторов и новые вопросы Fill Gap с вариантами/дистракторами остаются допустимыми; наличие вариантов не меняет оценивание или извлечение правильного ответа.
- Расписания Learning остаются отделены от результатов оценивания. Оркестрация Live остаётся отдельным ограниченным контекстом.
- Клиентские флаги никогда не предоставляют право определять личность, выбирать движок, менять состояние, выполнять оценивание, открывать результаты или раскрывать защищённые правильные ответы.
- Автоматические тесты используют локальные fake/stub-реализации и никогда не вызывают реальные OpenAI, Stripe, email-, storage- или другие платные/удалённые сервисы.
- Инженерное владение уже определено: #529 — единственная транзакция финальной сдачи; #543 отвечает за уникальность принятых ответов; #599 — за универсальные квитанции команд; #600 — за скрытый (`dark`) запуск; #609 — за публичную активацию; #603 — за автоматически оценённые факты; #566 — за классификацию неоцениваемых активностей; #607 — за агрегированные отчёты; #631 — за историю отдельной попытки; #585/#587/#655/#657 соответственно владеют границами Live-состояния, событий, outbox, проектора и публичного snapshot.

## Вопросы архитектурного каталога

### A01. Какой должна быть точная начальная схема политики?

**Владелец / срок принятия:** #612 и #515; **Фаза 0**.

**Решение:** Выбрать минимальный набор полей политики, который будет авторитетным в v1, включая выбор вопросов, доставку, навигацию, тайминг, ответы, оценивание, открытие результатов и ограничения.

**Простыми словами:** Здесь речь не о таблицах базы данных, а о «словаре правил» одной попытки. Нужно решить, какие параметры сервер обязан знать и сохранить уже в первой версии новой архитектуры: какие вопросы брать, как их показывать, можно ли перемещаться назад, есть ли таймер, как оценивать ответы и что раскрывать после завершения.

**Почему это важно для архитектуры:** Все последующие функции будут опираться на этот контракт. Слишком широкая v1-схема заставит заранее реализовать и поддерживать десятки пока неиспользуемых полей. Слишком узкая или нетипизированная схема приведёт к тому, что важные решения снова разъедутся по контроллерам и `if (mode == ...)`, от чего архитектура как раз уходит.

**Техническое пояснение:** Каждый блок политики должен быть типизированным и версионируемым. Неизвестная версия или неизвестная стратегия не должна молча заменяться значением по умолчанию: операция должна завершиться безопасным отказом до создания попытки.

**Пользовательский пример:** Мария открывает свой существующий тренировочный квиз по биологии из 20 вопросов. Сервер должен знать, выдаются ли все вопросы сразу, можно ли возвращаться назад, есть ли таймер и когда показываются ответы, не требуя от старого фронтенда новых полей.

**Развёрнутый сценарий:** Мария нажимает «Начать практику» в старом интерфейсе, который ничего не знает о новой policy-driven модели. Сервер сам выбирает встроенный preset, разрешает его в конкретную политику и сохраняет snapshot примерно со следующими фактами: опубликованная ревизия квиза, `ALL`-выбор, `ALL_AT_ONCE`, свободная навигация, отсутствие таймера, бинарное оценивание, неограниченное число будущих попыток и раскрытие результатов после финальной сдачи. Если через месяц preset изменится, уже начатая попытка продолжит жить по сохранённому snapshot.

**Варианты:**

- **A. Минимальная схема фиксированной практики:** только поля, необходимые для одного аутентифицированного, неограниченного по времени тренировочного пресета с фиксированной стратегией `ALL`; неизвестные поля приводят к безопасному отказу.
- **B. Широкая схема, заранее готовая к формальному оцениванию:** сразу включить задания, таймеры, попытки, ручное открытие результатов, разделы и специальные условия, даже если они пока неактивны.
- **C. Универсальный JSON-набор правил:** хранить произвольные именованные настройки, которые интерпретируют обработчики.

**Рекомендация:** A. Добавлять типизированные и версионируемые поля только тогда, когда их реально использует пресет; не создавать универсальный движок правил.

**Что означает рекомендация на практике:** Выбор A не запрещает таймеры, задания или accommodations навсегда. Он означает: в `schemaVersion: 1` включаются только поля, которые нужны первому реально работающему потоку, но границы объектов проектируются так, чтобы новые типизированные подполитики можно было добавлять совместимо.

### A02. Какие пресеты входят в первоначальный набор?

**Владелец / срок принятия:** #612/#516; **Фаза 0**.

**Решение:** Выбрать, какие понятные пользователю режимы выполнения первыми поставляются как поддерживаемые серверные пресеты.

**Простыми словами:** Нужно определить, какие пользовательские режимы действительно считаются готовым продуктом в первом релизе. Preset — это не отдельный движок и не ветка кода, а версионируемый набор значений одной общей политики.

**Почему это важно для архитектуры:** Если заранее объявить «формальный экзамен», но ещё не реализовать надёжные таймеры, limits, delayed release и защищённую навигацию, название режима будет обещать больше, чем реально гарантирует система. С другой стороны, один рабочий preset позволяет рано проверить всю архитектурную цепочку end-to-end.

**Техническое пояснение:** Новый conventional mode должен появляться прежде всего как preset, составленный из уже существующих typed policies. Он не должен добавлять новый набор контроллеров или разрастаться в центральный `switch` по имени режима.

**Пользовательский пример:** Автор нажимает «practice» для существующего квиза. Должен ли сервер предлагать только текущее поведение свободной практики либо также рекламировать формальный экзамен и самооценку, которые ещё не завершены?

**Развёрнутый сценарий:** Автор существующего квиза выбирает обычную практику. Сервер использует единственный поддерживаемый preset и создаёт воспроизводимую попытку. Кнопки «Timed assessment» или «Self-assessment» пока не показываются и не принимаются API, даже если соответствующие enum-значения уже обсуждаются в архитектуре. Позже они добавляются как новые версии конфигурации после собственных conformance-тестов.

**Варианты:**

- **A. Только один встроенный пресет свободной практики.**
- **B. Свободная практика плюс формальное задание с таймером.**
- **C. Свободная практика, формальное оценивание и неоцениваемая самооценка.**

**Рекомендация:** A. Добавлять B/C только после прохождения соответствующих проверок соответствия (`conformance gates`).

**Что означает рекомендация на практике:** Рекомендация A создаёт первый walking skeleton: один preset, но полностью через revision → resolved policy → persisted form → server commands → grading → release.

### A03. Какие поля пресета могут переопределять авторы?

**Владелец / срок принятия:** #680/#665; **До реализации управляемых пресетов**.

**Решение:** Определить, могут ли авторы изменять поведение пресета и какие поля остаются под контролем платформы.

**Простыми словами:** Preset задаёт безопасную базовую конфигурацию, а override позволяет автору изменить только отдельные разрешённые параметры. Нужно определить список таких «ручек» и пределы, в которых автор может их двигать.

**Почему это важно для архитектуры:** Без allow-list автор сможет случайно или намеренно ослабить правила безопасности — например, открыть ключ ответов до блокировки ответа или убрать обязательный дедлайн. Полный запрет overrides, наоборот, сделает presets слишком жёсткими для реальной учительской работы.

**Техническое пояснение:** При старте попытки сохраняются не только итоговые значения, но и provenance: какое значение пришло из preset, какое — из assignment override, а какое было ограничено immutable revision constraint. Runtime затем исполняет итоговый snapshot, а не перечитывает mutable preset.

**Пользовательский пример:** Учитель выбирает «formal assessment», но хочет 45 минут вместо 30 и разбор только с баллами, без показа ключа правильных ответов.

**Развёрнутый сценарий:** Учитель выбирает preset формального теста. Платформа разрешает ему выставить длительность от 10 до 180 минут, число попыток от 1 до 3 и выбрать, показать ли только итоговый балл или ещё объяснения после дедлайна. Он не может отключить server-side authorization, разрешить клиенту самому выбирать следующий вопрос или раскрыть правильные ответы во время редактируемой попытки.

**Варианты:**

- **A. Без переопределений:** авторы выбирают пресет строго в опубликованном виде.
- **B. Явный allow-list с платформенными границами:** например, длительность, количество попыток, число выбираемых вопросов и категории раскрываемой информации.
- **C. Любое поле политики или произвольное JSON-переопределение.**

**Рекомендация:** B. Проверять и сохранять в snapshot каждое переопределение; никогда не ветвить runtime-поведение по имени пресета.

### D02. Какое представление балла, точность и округление являются авторитетными?

Pass threshold 7000 сравнивается с authoritative ratio/normalized rule, а не со строкой «66.67%». Weighted questions могут использовать fixed-scale decimals, но scale и rounding version должны быть одними для grading, API и reports.

### D04. Какое действие создаёт неизменяемую опубликованную ревизию квиза?

- **A. Явное действие Publish создаёт ревизию; изменения остаются изменяемыми черновиками.**
- **B. Каждое сохранение автоматически публикуется.**
- **C. Первый старт участника делает snapshot и публикует текущее содержимое.**

### D36. Насколько быстро исправления/открытия обновляют отчёты и кэши?

**Владелец / срок принятия:** #679/#606/#607; **До активации отчётов**.

**Решение:** Определить SLO задержки проекции, маркер устаревания, вариативность кэша и различие текущей и исторических версий результата.

**Простыми словами:** Reports обычно читают derived projections, поэтому correction/release может появиться не мгновенно. Нужно выбрать SLO, stale/as-of marker и cache invalidation.

**Почему это важно для архитектуры:** Nightly update без индикатора показывает ложную актуальность. Recalculate raw answers на каждом request дорого, может расходиться с immutable result versions и создаёт N+1/full scans.

**Техническое пояснение:** Projection lag metrics/alerts и reconciliation обязательны. Cache key включает authorization/filter/version dimensions, чтобы correction/revocation не отдавала старые protected данные.

**Пользовательский пример:** Оценку исправляют в 10:00; учитель обновляет закэшированный отчёт в 10:01 и всё ещё видит старое среднее по когорте.

**Развёрнутый сценарий:** Grade corrected в 10:00. Event/outbox запускает idempotent projection update; к 10:01 report может ещё показывать old value, но содержит `asOf=09:59:58`/`stale=true`. В пределах, например, пяти минут projection становится current, cache invalidates по assignment/result version. Old result остаётся historical и не участвует в current average.

**Варианты:**

- **A. Отчёты используют текущую неизменяемую версию после идемпотентной проекции, показывают ограниченное устаревание/`as-of`, инвалидируют кэши с учётом авторизации, а старые версии сохраняют только как историю.**
- **B. Обновлять ночью без индикатора устаревания.**
- **C. Пересчитывать из сырых ответов при каждом запросе.**

**Рекомендация:** A. До #606 выбрать первоначальный SLO задержки проекции, например менее пяти минут, с алертами.

**Что означает рекомендация на практике:** Рекомендация A требует выбрать numeric SLO до реализации, но не обещает synchronous report transaction.

### D37. Какие правила часового пояса и ручного переопределения применяются к запланированному открытию результатов?

**Владелец / срок принятия:** #675/#697/#633/#634; **До реализации запланированного открытия**.

**Решение:** Выбрать хранение в виде точного момента времени, обработку локальной зоны автора, неоднозначности DST и приоритет ручного и запланированного открытия.

**Простыми словами:** Author задаёт local date/time, но система должна превратить его в один неизменяемый UTC instant. Нужно решить DST ambiguity и гонку manual/scheduled release.

**Почему это важно для архитектуры:** Local time может быть nonexistent при spring-forward или двусмысленным при fall-back. Recompute timezone rules каждый worker run может изменить уже опубликованное решение.

**Техническое пояснение:** `first committed release wins` не означает запрет revoke/correction: это отдельные authorized transitions. Worker использует persisted instant и server Clock.

**Пользовательский пример:** Учитель планирует открытие на 09:00 `Europe/London` в день перехода на летнее/зимнее время, а затем вручную открывает результаты в 08:55, когда worker уже скоро должен сработать.

**Развёрнутый сценарий:** Teacher выбирает 09:00 Europe/London. При publication backend resolves ZoneId rules и сохраняет exact Instant вместе с original local/zone provenance. Если время ambiguous/nonexistent, публикация просит выбрать offset или исправить значение. В 08:55 manual release commits; scheduled worker в 09:00 видит state AVAILABLE и idempotently ничего не меняет. Если worker был первым, manual command возвращает previous success/current state.

**Варианты:**

- **A. При публикации разрешать локальные дату/время+зону автора в один сохранённый UTC instant; отклонять неоднозначные или несуществующие локальные моменты, если выбор явно не уточнён; первый зафиксированный release выигрывает идемпотентно.**
- **B. Хранить локальный текст и пересчитывать его при каждом запуске worker.**
- **C. Запланированное открытие всегда перезаписывает состояние ручного открытия.**

**Рекомендация:** A.

**Что означает рекомендация на практике:** Рекомендация A исключает DST и race ambiguity.
