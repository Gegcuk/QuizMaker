### Recovery readiness while keeping the existing VPS

The owner's deployment refinement settles the current sequence: retain the small-VPS assumption and prepare separable backend/frontend/database/storage boundaries. It defers vendor, machine sizing, cluster spend and numerical RTO selection. Q74 still requires zero loss of confirmed examination/balance data in its defined failure scenario when that guarantee is activated; a single disk cannot prove it. Preparing this design does not claim the current installation meets it.

**Accepted preparation:** keep the current application and make persistence, storage and worker boundaries location-independent. A project-owned storage port exposes streamed content and stable key/version metadata; current local or existing S3 storage stays behind its adapter. Database endpoints are configurable; frontend calls the backend API; durable jobs, attempt state, idempotency and recovery records live in authoritative shared persistence. Later, moving files/database does not change a learner's saved attempt identity or expose server filesystem paths. No new S3-compatible daemon on the same VPS is part of this preparation; it would add operating cost without an independent failure domain. Migration still needs real data transfer and verification.

Specific design boundaries to implement in the relevant future slices:

- Keep confirmed answers, revisions, balances, delivery/settlement facts and idempotency in shared transactional persistence. Local caches or in-process queues are not the sole authority. Server-side transactions remain short; no database transaction waits on transcription/upload. Commit the transcript/billing publication only after durable content success, with explicit recovery for the gap.
- Store immutable original/content version references using bounded IDs/generations. Storage ports stream bytes; callers do not rely on local absolute paths, shared mounts or reread/hash entire large files for version checks. Temporary staging remains distinguishable from retained authoritative sources.
- Existing durable worker claims and recovery checkpoints must survive restart and multiple backend instances. Adding a balancer must not cause duplicate charges, replayed answers or two workers consuming the same recording budget. In-flight temporary work can be recovered only according to its existing idempotency/outcome semantics.
- Preserve credentials/configuration, schema migration state, exact content versions and authorized erasure records as part of a real recoverable installation. Restore access stays closed until Q65 deletion replay and integrity checks complete; replaying recovery does not send duplicate notifications or repeat charges.

Later operational alternatives are concrete but not selected: a managed MySQL deployment with independently durable replication plus external object storage (for example, [RDS Multi-AZ synchronously replicates to another availability zone](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html)); or a self-operated MySQL InnoDB Cluster with independently placed nodes and durable storage, useful for isolated/on-premise installations. [MySQL requires three group members to continue after one failure](https://dev.mysql.com/doc/refman/8.4/en/group-replication-fault-tolerance.html); [transaction-consistency/failover settings](https://dev.mysql.com/doc/refman/8.4/en/group-replication-configuring-consistency-guarantees.html), disk durability and storage publication need explicit verification. Three containers on one VPS are not three independent copies. A second backend/balancer improves service availability but does not replicate the database by itself.

Choose/price those operating schemes later against actual load and budget. A provider's [typical 60–120-second RDS failover](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.Failover.html) is not QuizMaker's end-to-end recovery promise. Scheduled backups/PITR protect other recovery scenarios but do not by themselves ensure Q74's zero acknowledged-data loss. Before claiming that outcome, deliberately lose a working node/disk and verify acknowledged answers, ledger facts and exact required originals, reconcile interrupted operations and measure when safe service resumes. Example: a pupil's saved answer remains after recovery, but this does not grant an automatic timer pause/extension or extra attempt. Existing policy and authorized compensation remain unchanged.
